守ること：

2. main に直接コミットしてよい。force push はしない。push の前に main の最新を取得し、ほかのコミットがあれば rebase してから push する。git が使えない環境なら、GitHub API で main にファイル単位でコミットする（既存ファイルは blob SHA を指定）。

4. push に失敗したら一度だけ再試行し、だめなら会話に報告して次の区切りへ進む（次の push でまとめて送る）。

## 途中で止まっても使えるように

- あなたは容量の上限で止まることがあります。**区切りを終えたらすぐ push** してください。一つの区切りが長くなりそうなら、途中で `S<k> partial` として push してかまいません（その場合は `S<k>.md` を後で追記してよい）。
- **最初に S0 だけを済ませて push** してください。これで、どこで止まっても状態がリポジトリから読めます。
- 価値の高い区切りから順に並べてあります。どこで止まっても、それまでの push がそのまま使えるデータになります。
- 会話で「続けて」と言われたら、`STATUS.md` を読み、次の区切りから再開してください（終わった区切りはやり直さない）。

## 負担を抑えるために

- 各 `S<k>.md` は 150 行程度まで。原稿の文を書き写さず、行番号で指してください。
- 判定は表で：`| 主張 | 行 | 判定 | 根拠（一、二文） |`。判定は **OK**（確認できた）、**GAP**（結論は正しいが補うべき穴がある。何を補えば閉じるか書く）、**FALSE**（書いてあるとおりには偽。具体的な反例を書く）、**UNCHECKED**（今回は確認できなかった）。文献の確認では **OK／MISCITED（典拠が主張を支えない）／OVERCLAIM（典拠より強く言っている）／UNVERIFIED（典拠を開けなかった）** を使ってください。
- 計算は任意。する場合は Python 標準ライブラリのみ、$n\le4$ 程度。有限計算は証明の代わりにならないことを明記。
- ウェブ検索は S2・S5・S6 で使ってよい（使えない環境なら UNVERIFIED と書いて先へ進む）。
- 新しい定理や大きな構成の変更の提案は不要（気づいたことは各区切りの末尾に 3 行以内で）。

## findings.csv の列

`id,section,severity,location,lines,claim,issue,suggested_fix`

- `id` は `B01` から通し番号（前回の `A01`〜 と区別するため）。
- `severity` は `false`（反例あり）、`gap`、`miscited`、`overclaim`、`major`（数学以外の重大な問題）、`minor`、`typo` のどれか。

最優先は **FALSE・GAP と、典拠が主張を支えていない箇所を見落とさないこと**です。問題が見つからなかった主張についても、なぜ OK と言えるかを一、二文で書いてください。
